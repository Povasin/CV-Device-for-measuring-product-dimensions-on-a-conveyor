## 1. Executive summary

Предлагается программно-аппаратный комплекс **Conveyor Dimensioning System**: три синхронизированные depth-камеры наблюдают товар, система выделяет его геометрию относительно плоскости ленты, строит объединённое облако точек, оценивает минимальный по объёму ориентированный ограничивающий параллелепипед и передаёт результат в WMS.

Базовое решение использует классическую 3D-геометрию: нейросеть не включается без подтверждённой необходимости. Основной кандидат для прототипа — RealSense D455; это не означает, что он доказанно обеспечивает требуемую точность. Первым техническим gate является проверка малых товаров, движения и сложных материалов. Если gate не пройден, архитектура переключается на лазерные профиломеры.

Обязательный результат задания — PDF. Код, demo и GitHub-репозиторий являются дополнительными артефактами, которые делают решение проверяемым.

## 5. Requirements

Для эталонного размера \(d_i\) допуск равен:

\[
T_i=\max(0.05d_i,\;5\text{ мм}).
\]

Товар считается успешно измеренным только при:

\[
|\hat d_i-d_i|\leq T_i
\]

для всех трёх размеров одновременно. \(d_i\) — независимый ground truth, а не предсказанное значение.

| Requirement | Способ проверки |
|---|---|
| Три габарита | Сравнение с независимым эталоном. |
| Минимальный box | Геометрические тесты и независимый решатель. |
| Скорость 1 м/с | Реальные записи или стенд с измеренной скоростью. |
| Границы диапазона | Отдельные испытания на 10 мм и на максимальных размерах. |
| WMS | Интеграционные тесты доставки, повторов и отказов. |

## 6. Constraints

Допущения, требующие проверки до финального заявления о готовности:

1. Товар находится на ленте отдельно от других товаров.
2. При fusion во времени он не деформируется и не проскальзывает.
3. Система может вернуть контролируемый отказ вместо недостоверного размера.
4. WMS получает идентификатор измерительного события; связь с SKU находится вне текущего scope.
5. Порядок рёбер box согласован с WMS.

Контролируемый отказ — правильное поведение, но не является успешным измерением и остаётся в знаменателе метрик покрытия.

## 7. Предлагаемая архитектура

```text
Триггер + 3 синхронизированные depth-камеры
                    │
                    ▼
      Сбор кадров и проверка синхронизации
                    │
                    ▼
    Калибровка → сегментация → облака точек
                    │
                    ▼
      Преобразование в координаты конвейера
                    │
                    ▼
      Fusion ракурсов → фильтрация → MVBB
                    │
                    ▼
  Проверка качества → durable outbox → WMS
```

Первый рабочий режим использует один синхронный комплект кадров, чтобы не зависеть от модели движения. Объединение кадров во времени добавляется только после доказательства необходимости.

## 11. Размещение сенсоров

Координаты: \(X\) — направление ленты, \(Y\) — поперёк, \(Z\) — вверх. Начало — центр измерительной зоны на поверхности ленты.

| Элемент | Исходная проектная позиция |
|---|---|
| Measurement zone | X=[−400;400] мм, Y=[−300;300] мм |
| Верхняя C1 | (0, 0, 1250) мм, вниз |
| Диагональная C2 | (−850, −750, 850) мм, в центр зоны |
| Диагональная C3 | (850, 750, 850) мм, в центр зоны |
| Trigger | X≈−600 мм |
| Следующий узел, пример | X≈1500 мм |

```text
ВИД СВЕРХУ, X →

               C3 ↙
Y=+300  ┌──────────────────────────────┐
        │       measurement zone       │
trigger │        C1 ↓   товар          │ → следующий узел
   │    │                              │
Y=-300  └──────────────────────────────┘
               ↗ C2

ВИД СБОКУ
                    C1, Z≈1250 мм
                           ↓
      C2 ↘         товар          ↙ C3
Z=0 ════════════════конвейер══════════════════════→ X
```

Для коробки 400×300 мм при повороте её проекция по ленте может быть 500 мм. Консервативная диагональ допустимого параллелепипеда:

\[
D=\sqrt{400^2+300^2+300^2}\approx583\text{ мм}.
\]

Размещение выше — отправная точка, а не утверждённый монтаж. Полный FOV проверяется ray-casting по углам рабочего объёма.

## 12. Калибровка

| Вид | Процедура | Результат |
|---|---|---|
| Intrinsic | Мишень в 20–30 пригодных позах, центр и края | \(f_x,f_y,c_x,c_y\), дисторсия |
| Межкамерная | Общая мишень во многих позах | transforms камера↔камера |
| Camera→conveyor | Мишень и известная плоскость ленты | \(T_{conveyor\leftarrow camera}\) |
| Depth | Плоскости/меры на разных дистанциях | Bias, шум, поле применимости |
| Conveyor plane | Пустая лента и остатки модели | Нормаль, смещение, карта стабильности |
| Scale | Независимые размеры по X/Y/Z | Ошибка в мм |
| Временная | Синхронный световой/движущийся тест | Межкамерное рассогласование |

Калибровочный артефакт хранит serial number, режимы, единицы, дату, calibration ID, transforms, контрольные ошибки и checksum.

Повторная калибровка требуется после перемещения камеры, ремонта, смены режима/оптики, выхода контрольной меры за пределы или заметного дрейфа. Reprojection error не является доказательством метрической точности. [OpenCV](https://docs.opencv.org/4.13.0/dc/dbb/tutorial_py_calibration.html).

Для D400 предусмотрена аппаратная синхронизация, но она требует отдельной проверки на готовом стенде. [RealSense multi-camera](https://dev.realsenseai.com/docs/multiple-depth-cameras-configuration/).

## 13. CV pipeline

| Этап | Вход → выход | Метод | Сложность | Failure mode |
|---|---|---|---|---|
| Trigger | Сигнал → event | Детерминированная state machine | O(1) | Пропуск/дубликат |
| Acquisition | Потоки → кадры+metadata | SDK | O(P) | Disconnect/потеря кадра |
| Sync | Кадры → FrameBundle | HW sync, counters, timestamps | O(C) | Несовпадающие моменты |
| Preprocessing | Depth → валидный depth | Invalid mask, range, ROI | O(P) | Неверный scale/NaN |
| Deprojection | Depth → точки камеры | Модель камеры | O(N) | Неверные intrinsics |
| Transform | Точки → conveyor frame | SE(3) | O(N) | Неверное направление матрицы |
| Plane removal | Сцена → кандидаты | Калиброванная плоскость | O(N) | Удалён низкий товар |
| Segmentation | Кандидаты → объект | Связность/геометрия | O(P) | Малый объект принят за шум |
| Fusion | Облака → общее облако | Extrinsics | O(N) | Двоение границы |
| Filtering | Облако → inliers | Локальная поддержка | O(N log N) | Удалён выступ |
| Coverage | Маски+точки → score | ROI, visibility, согласование | O(N+P) | Невидимое принято за отсутствующее |
| Hull | Точки → convex hull | Open3D/Qhull | Зависит от N | Вырожденность |
| MVBB | Hull → box | Выбранный backend | O(KH) | Неверная минимальность |
| Quality | Box → result/reject | Правила качества | O(N) | Ложный success |
| Delivery | Result → WMS ACK | SQLite outbox + HTTP | Сеть | Timeout/повтор |

Глобальные правила: внутренние координаты — мм и `float64`; невалидный результат не заменяется нулями; исходные и производные версии calibration всегда трассируемы.

## 14. Алгоритм измерения

Для множества точек \(S\) ищется:

\[
R^*=\arg\min_{R\in SO(3)}
\prod_{j=1}^{3}\left(
\max_{p\in S}(R^\top p)_j-
\min_{p\in S}(R^\top p)_j
\right).
\]

| Метод | Роль | Ограничение |
|---|---|---|
| AABB | Диагностика и ROI | Зависим от позы товара |
| PCA OBB | Быстрый baseline | Не минимизирует объём |
| 2D rotating calipers + height | 2.5D baseline | Не решает общую 3D-задачу |
| Hull-face OBB | Быстрая аппроксимация | Может пропустить optimum |
| 3D MVBB | Основной метод | Нужна проверка backend и скорости |

Порядок принятия реализации:

1. Построить AABB и 2.5D baseline.
2. Использовать 3D MVBB через изолированный geometry adapter.
3. Зафиксировать версию backend до реализации.
4. Проверить containment, устойчивость к перестановке точек и инвариантность к transform.
5. Сравнить результаты с независимым решателем и аналитическими случаями.

Open3D `latest` документирует `MINIMAL_JYLANKI`, но проверенный релиз 0.19 имеет иной интерфейс. Установка должна быть привязана к версии, где нужный API действительно доступен. [Open3D latest](https://www.open3d.org/docs/latest/python_api/open3d.t.geometry.OrientedBoundingBox.html), [Open3D 0.19](https://www.open3d.org/docs/release/python_api/open3d.t.geometry.OrientedBoundingBox.html).

Алгоритм Jylänki практичен, но автор отмечает отсутствие формального доказательства глобальной оптимальности; это необходимо честно описать в отчёте. [Jylänki](https://clb.confined.space/minobb/minobb.html). Для независимого сравнения подходит Geometric Tools, который также должен быть обозначен как численная процедура. [Geometric Tools](https://www.geometrictools.com/Documentation/MinimumVolumeBox.pdf).

Нельзя автоматически достраивать невидимую поверхность. Выход содержит три ребра MVBB, rotation, центр и отдельно высоту над лентой; канонический порядок рёбер задаётся контрактом WMS.

## 15. Classical CV vs DL

Нейросеть в базовом варианте не требуется.

| Подзадача | Выбранный подход | Когда оправдан DL |
|---|---|---|
| Detection | Trigger и изменение сцены | Неконтролируемый сложный фон |
| Segmentation | Плоскость ленты, высота, связность | Систематический failure геометрии после диагностики |
| Depth | Физический depth-сенсор | Только отдельное исследование заполнения пропусков |
| Dimensions | Метрическая 3D-геометрия | Не оправдано прямое предсказание размеров |

DL не устраняет отсутствие метрических данных прозрачной или полностью скрытой поверхности. Если нейросеть появится, требуются отдельные постановка, dataset, разметка, split, inference budget и ablation.

## 16. Error budget

Ниже — проектные пределы вклада в строгий допуск 5 мм, а не измеренные характеристики hardware.

| Источник | Целевой вклад, мм | Влияние | Мера |
|---|---:|---|---|
| Depth noise и residual bias | 1.3 | L/W/H | Режим, дистанция, depth calibration |
| Межкамерная калибровка | 0.5 | Двоение краёв | Общая мишень |
| Дисторсия | 0.2 | Края FOV | Модель и проверка по полю |
| Pixel quantization | 0.7 | Поперечные размеры | Физическое разрешение |
| Segmentation | 0.5 | Недомер/перемер | Boundary validation |
| Motion blur | 0.4 | X | Короткая экспозиция |
| Вибрации | 0.2 | Все оси | Жёсткая рама |
| Plane estimate | 0.3 | Высота | Контроль ленты |
| MVBB numerics | 0.2 | Все размеры | Независимые тесты |
| Sync | 0.3 | Fusion | HW sync |
| Temperature drift | 0.2 | Scale/offset | Прогрев и мониторинг |
| Резерв | 0.2 | — | Не расходовать заранее |

Отражения и окклюзия не получают фиктивного численного вклада: они могут давать систематический failure, поэтому нужны test coverage и controlled rejection.

Для непрозрачных жёстких товаров ±5 мм — реалистичная цель, но не подтверждённый факт. Для 10-мм, чёрных, прозрачных, блестящих и тонких объектов это высокий риск. Провал должен менять сенсор или размещение, а не маскироваться средней ошибкой.

## 17. Latency budget

Для зоны длиной 800 мм:

\[
t_{full}=\frac{800-L_X}{1000}.
\]

Для консервативной длины \(L_X=583\) мм: \(t_{full}\approx217\) мс. При 30 FPS доступно около 6–7 моментов, до учёта потерь и FOV.

| Этап | Проектный бюджет |
|---|---:|
| Ожидание комплекта | 34 мс |
| Получение/проверка кадров | 20 мс |
| Предобработка | 15 мс |
| Deprojection/transforms | 25 мс |
| Segmentation | 15 мс |
| Fusion/filtering | 25 мс |
| Convex hull | 20 мс |
| MVBB | 80 мс |
| Quality | 5 мс |
| Local save | 10 мс |
| WMS delivery/ACK | 50 мс |
| **Итого** | **299 мс** |

Это целевой budget. Реальный допустимый deadline зависит от положения следующего конвейерного узла и его времени реакции, которых в задании нет. Сквозные P50/P95/P99 измеряются отдельно, не суммой P95 этапов.

## 19. Metrics

Главная метрика:

\[
\text{All-dimensions pass rate}=\frac{\text{товары, у которых все три размера в допуске}}{\text{все предъявленные товары}}.
\]

Также измеряются по каждой оси: MAE, RMSE, signed bias, MAPE, P50/P95/P99 абсолютной ошибки, максимальная ошибка и доля в допуске.

Нормализованная ошибка:

\[
e_i^{norm}=\frac{|\hat d_i-d_i|}{\max(0.05d_i,5)}.
\]

\(e_i^{norm}>1\) означает нарушение требования.

| Группа | Метрики |
|---|---|
| Доступность | Valid measurement rate, rejection rate |
| Поток | Missed object rate, duplicate event rate |
| Время | Latency P50/P95/P99, deadline misses |
| Производительность | Товары/мин, FPS, очереди |
| Геометрия | Containment, сравнение объёма с reference solver |
| Delivery | ACK time, retries, outbox depth |
| Ресурсы | CPU, RAM, точки и вершины hull |

## 20. Failure cases

| Scenario | Cause | Expected behavior | Detection | Mitigation | Severity |
|---|---|---|---|---|---|
| Чёрный товар | Слабый depth signal | Измерение либо reject | Invalid depth/нестабильность | Свет, режим, другой сенсор | High |
| Прозрачный | Преломление/фон | Не выдавать уверенный размер без доказательств | Противоречие сенсоров; не всегда наблюдаемо | Спецоптика/исключение | Critical |
| Блестящий | Reflections | Reject при конфликте ракурсов | Выбросы/разрывы | Ракурс, свет | High |
| Очень малый | Недостаток пикселей | Не удалять как шум; иначе reject | Размер компоненты/поддержка | Оптика/разрешение | Critical |
| Очень большой | Обрезан FOV | Reject | Касание ROI | Изменить FOV | High |
| Два близких товара | Слияние | Разделить или reject | Trigger + components | Контроль потока | High |
| Partial occlusion | Невидимая часть | Не заявлять полный результат | Coverage score | Доп. ракурс | High |
| Motion blur | Длинная экспозиция | Отбросить комплект | Нестабильные границы | Экспозиция | High |
| Calibration drift | Сдвиг камеры | Запрет valid results | Контрольная мера | Recalibrate | Critical |
| Sensor disconnect | Кабель/питание | Явный error | Timeout/heartbeat | Recovery | High |
| WMS unavailable | Сеть/сервер | Durable retry | Timeout/HTTP error | Outbox/backoff | High |

## 23. Testing strategy

| Уровень | Сценарий | Acceptance criterion |
|---|---|---|
| Unit transforms | Identity/inverse/composition | Ошибка ниже numerical epsilon |
| Unit input | NaN, Inf, пустые и неверные shapes | Предсказуемый reject/error |
| Unit geometry | Куб, box, sphere, degeneracy | Верные размеры/классификация |
| Unit tolerance | Переход 5 мм ↔ 5% | Верная формула |
| Synthetic orientation | Повороты по всем осям | Размеры invariant |
| Synthetic visibility | Невидимая грань/выступ | Coverage/reject корректен |
| Integration | Replay→pipeline→mock WMS | Сквозной результат |
| Delivery | Timeout, 500, restart | Нет потери event; idempotency |
| Regression | Фиксированные реальные записи | Нет принятой регрессии |
| Hardware | 1 м/с, меры, disconnect, shift | Точность или честный reject |
| Performance | Длинная серия | Очередь не растёт, latency измерена |

Обязательный synthetic case: box 200×100×50 мм, произвольные SE(3)-повороты, перестановка и дублирование точек. Для идеальной геометрии цель проверки backend — ошибка не более 0.25 мм, значительно строже пользовательского допуска.

## 25. Benchmark

План: 1000 базовых синтетических сцен, split 600/200/200, пять сенсорных условий на сцену, итого 5000 обработок. Все вариации одной сцены находятся в одном split.

Переменные: размеры, форма, поза, положение, noise, depth holes, edge outliers, окклюзия, extrinsic shift, sync offset, движение.

Сравнения: AABB, PCA OBB, 2.5D baseline, выбранный 3D backend; один и три ракурса; filtering on/off; полное и наблюдаемое облако.

Графики: CDF ошибки, ошибка против размера/угла/доли пропусков, pass rate по категориям, latency против N/H, ошибки и rejection rate, отдельные панели synthetic и real data.

| Локальная файловая система | Да | Только проект | Код, docs, diff |
| Web research | Да | Read-only | Datasheets и docs |
| Documentation | По необходимости | Read-only | API, совместимость версий |
| GitHub | Не в baseline | Минимальные, один repo | PR/issues при появлении repo |
| WMS MCP | Нет | — | Достаточен HTTP adapter |
| Database MCP | Нет | — | Достаточен SQLite |

Не подключать Slack, почту, CRM и нерелевантные коннекторы. MCP — механизм доступа к инструментам, а не компонент CV-системы. [MCP documentation](https://learn.chatgpt.com/docs/extend/mcp?surface=cli).

## 34. Git workflow

- `main` содержит воспроизводимую версию.
- Короткие ветки: `feat/geometry`, `feat/replay`, `feat/wms`.
- Один commit — одно логическое изменение, например `feat: add calibrated point transforms`.
- Review обязателен для geometry, calibration, metrics и hardware decisions.
- Не использовать GitFlow; не коммитить секреты, cache, environments и большие записи.

## 36. Red Team critique

| Причина отклонения | Ответ в плане |
|---|---|
| «Показаны только коробки» | Неправильные формы, materials и реальные записи |
| «Три камеры выбраны без расчёта» | FOV/ray-casting и сравнение одного/трёх ракурсов |
| «D455 не доказывает ±5 мм» | Ранний physical gate и переход к профиломерам |
| «Измеряется облако, а не товар» | Coverage validation и явные ограничения наблюдаемости |
| «PCA выдан за optimum» | Отдельный MVBB backend и baseline-сравнения |
| «API нет в release» | Проверка конкретной версии до реализации |
| «Synthetic равно hardware validation» | Разделение synthetic/static/moving validation |
| «Средняя ошибка скрывает провалы» | All-dimensions pass rate, max и percentiles |
| «Эталон сделан тем же кодом» | Аналитические случаи и независимый измерительный контур |
| «Слишком много инфраструктуры» | Один процесс, SQLite outbox, исходящий HTTP client |

## 37. Итоговый порядок реализации

1. Зафиксировать requirements, units, MVBB-definition и WMS event contract.
2. Проверить availability геометрического backend, FOV и sensor feasibility.
3. Реализовать и проверить geometry core на аналитических формах.
4. Добавить replay с синтетическими depth-кадрами.
5. Выполнить calibration и ранние физические испытания маленьких товаров и 1 м/с.
6. Принять или отклонить RGB-D-архитектуру по результатам gate.
7. Добавить segmentation, fusion, coverage-quality gates и controlled rejects.
8. Реализовать events, outbox и WMS adapter.
9. Провести независимую validation и benchmark.
10. Подготовить demo, README, PDF и финальный audit.

Первое решение, которое нельзя откладывать: способна ли выбранная RGB-D-конфигурация измерять 10–30-мм объекты с требуемым допуском в рабочей зоне. До положительного доказательства итоговая точность системы не заявляется.
